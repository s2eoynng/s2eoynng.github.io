# 작업 워크플로우 규칙

이 문서는 Kiro가 이 프로젝트에서 작업할 때 항상 따르는 규칙입니다.

## 1. 커밋 & Git 워크플로우

### 매 작업마다 커밋 확인
- 하나의 작업(기능 추가, 수정, 리팩터링 등)을 끝낼 때마다, 커밋할지 사용자에게 물어본다.
- 사용자가 승인하면 커밋한다. 승인 없이 임의로 커밋하지 않는다.
- 커밋할 파일은 작업과 관련된 것만 명시적으로 스테이징한다 (`git add .` 지양).
- 커밋 메시지는 간결한 한국어 또는 영어로, 변경 내용이 드러나게 작성한다.
- `.env`, 자격증명 등 비밀이 들어갈 수 있는 파일은 커밋 전에 반드시 사용자에게 알린다.

### 작업 종료 시 PR & Merge (GitHub CLI 사용)
작업 세션을 마무리할 때, 연결된 `gh` CLI(계정: s2eoynng)를 사용해 다음을 수행한다.

1. **브랜치 push**: 변경사항을 새 브랜치에 push 한다. `main`에 직접 push 하지 않는다.
   - 새 브랜치는 `-u` 플래그로 원격 추적을 설정한다.
2. **PR 생성**: `gh pr create`로 PR을 만든다.
   - 제목은 70자 이내로 간결하게.
   - 본문에는 변경 요약, 테스트한 내용, 보류된 항목을 포함한다.
3. **Merge**:
   - 기본값: merge는 되돌리기 어려우므로 **사용자에게 확인을 받은 뒤** `gh pr merge`로 병합한다.
   - 단, 사용자가 해당 작업에 대해 "자동 merge" 또는 "알아서 merge"라고 명시하면 확인 없이 병합한다.
   - 병합 방식은 기본 squash merge(`--squash`)를 사용하되, 사용자가 다른 방식을 지정하면 그에 따른다.

### Git 안전 규칙
- `git config`는 변경하지 않는다.
- 파괴적 명령(force push, `reset --hard`, `clean -f`, 브랜치 강제 삭제)은 사용자의 명시적 허락 없이 실행하지 않는다.
- hook을 건너뛰지 않는다 (`--no-verify` 금지, 사용자가 명시하지 않는 한).

## 2. Notion 작업 기록

모든 의미 있는 변경 사항은 Notion MCP를 통해 **"임서영_홈페이지 프로젝트 기록"** 에 기록한다.

### 기록 시점
- PR을 생성하거나 작업을 마무리하는 시점에 기록한다.
- 사소한 오타 수정 등 아주 작은 변경은 묶어서 한 번에 기록해도 된다.

### 기록 방법
1. 기록 장소와 저장 절차는 `project-notes.md`를 따른다. 페이지를 검색하지 말고 거기 적힌 페이지 ID를 사용한다.
2. 저장 전에 변경 내용을 미리보기로 보여주고, 사용자가 확인한 뒤에만 저장한다.
3. 각 기록에는 다음을 포함한다.
   - 날짜
   - 작업 요약 (무엇을 왜 바꿨는지)
   - 변경된 주요 파일
   - 관련 커밋 또는 PR 링크 (있으면)

### 주의
- Notion MCP 서버가 연결되어 있지 않으면, 기록을 시도하기 전에 사용자에게 알린다.
- "임서영_홈페이지 프로젝트 기록" 대상을 찾지 못하면, 임의의 위치에 만들지 말고 사용자에게 어디에 기록할지 확인한다.

## 3. 일반

- 응답과 커밋/기록은 기본적으로 한국어로 작성한다.
- 코드 변경 후에는 가능한 경우 빌드/테스트로 검증한 뒤 작업 완료를 보고한다.
- 검증에 사용한 임시 파일은 정리한다.
